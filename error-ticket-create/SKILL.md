# /error-ticket-create — 원본 티켓 후속 에러 티켓 생성

## 목적

원본 티켓(`/ticket-create` 로 만들어 `/impl-*` 로 구현 → commit-push-merge 까지 끝난 티켓)에서 운영 중 발견된 오류를 별도 작업 단위로 분리한다. 사용자가 자연어로 던진 증상·의도·변경점을 받아 `docs/error/_template.md` 포맷의 에러 티켓을 만든다. 이 스킬은 **§1·§2·§3 까지** 작성하고, 실제 코드 수정은 후속 `/impl-api` 또는 `/impl-front` 가 담당한다.

---

## 호출 형식

```
/error-ticket-create <원본_티켓_파일명> <증상 + 의도한 내용 또는 변경점 자유 텍스트>
```

- `<원본_티켓_파일명>`: 확장자 없이 (예: `TRIX_EDITOR_INTEGRATION`). `docs/tickets/working/` 또는 `docs/tickets/done/` 에 존재해야 함.
- 인자가 부족하면 **즉시 중단**하고 사용자에게 누락 인자를 물어본다. 추측 금지.

---

## 사전 읽기 (필수)

에러 티켓 작성 전 아래 문서를 **Read 도구로 순서대로** 읽는다.

1. `docs/error/_template.md` — 에러 티켓 포맷
2. `docs/SSOT.md` — 프로젝트 규칙
3. 원본 티켓: `docs/tickets/{working|done}/<원본_티켓_파일명>.md`
4. 관련 구현 보고서(있으면): `docs/analysis/[<상대경로>/]<파일명>_report.md` (대괄호는 옵셔널 — 평탄 티켓이면 상대경로 슬래시 생략) — 원본 티켓 경로에서 `docs/tickets/[working|done|...]/` 접두를 제거하고 `docs/analysis/` 를 접두로 붙인 위치 (`/finalize-impl` 의 도출 규칙과 동일). 더블 슬래시 금지. 또는 `Glob` 으로 `docs/analysis/**/*_report.md` 탐색
5. `docs/ARCHITECTURE.md` (관련 도메인 파악용, 필요 시)

원본 티켓을 찾지 못하면 중단하고 사용자에게 정확한 파일명을 요청한다.

## 워크플로우

### 1. 원본 티켓 위치 확인

```
docs/tickets/working/<원본_티켓_파일명>.md
docs/tickets/done/<원본_티켓_파일명>.md
```

`Glob` 로 두 위치를 모두 확인. 둘 다 없으면 중단.

원본 티켓에서 다음을 추출하여 메타데이터로 보존한다:
- Type / Layer
- 영향 파일 후보 (Context §3 의 관련 파일 목록)

### 2. 관련 구현 보고서 탐색 (선택)

원본 티켓의 키워드로 `docs/analysis/` 하위 보고서를 찾는다.

```
Glob: docs/analysis/*<원본_티켓_키워드>*report*.md
```

찾으면 보고서의 §3 구현 상세를 참조해 §3 근본 원인 절의 "기존 코드 흐름" 추적에 활용. 못 찾으면 헤더의 `관련 보고서:` 칸은 `(없음)` 으로 표기.

### 3. 사용자 입력 분석 — 증상 / 의도 / 수정 방향 추출

사용자의 자유 텍스트에서 다음 슬롯을 채운다:

- **증상 (§1)**:
  - 콘솔/로그 에러 메시지 원문
  - 발생 위치 (파일:라인 또는 트리거 액션)
  - 재현 조건 (데이터 / 사용자 액션)
  - 영향 범위 (어떤 기능/화면/API 가 막히는가)
- **요약 (§2)** — 한 줄씩:
  - 의도(Intent): 원본 코드가 무엇을 하려 했는가
  - 실제(Actual): 어디서 어떻게 어긋났는가
  - 수정 방향(Fix Direction): 어떤 발상으로 풀 것인가

**모호하거나 누락된 항목이 있으면 반드시 사용자에게 질문한다.** 추측 금지. 질문해야 하는 대표 상황:

- 콘솔/로그 에러 원문이 없음
- 재현 조건 또는 영향 범위가 불명확
- 수정 방향이 두 가지 이상 가능 (사용자에게 선택 요청)
- 라이브러리/외부 모듈 변경이 필요한지 모호 → MIT/Apache 2.0/GPL 등 무료 라이선스 기준으로만 제안
- 원본 티켓 Scope 의 금지 항목을 침범할 가능성

### 4. 근본 원인 분석 — §3 작성을 위한 코드 탐색

원본 티켓의 영향 파일과 사용자가 지목한 위치를 기준으로 `Grep` / `Read` 로 코드를 분석한다. §3 의 4개 하위 절을 채울 재료를 모은다:

- §3.1 컨텍스트: 외부 라이브러리/프레임워크 출력 형식, 인코딩 정책 등 사건의 전제
- §3.2 기존 코드 흐름: 버그가 있는 핵심 코드 스니펫 + "단계 / 처리 / 결과" 3열 추적표
- §3.3 깨지는 지점: 파서/런타임이 어디서 의미를 잃는지 한 글자 단위 분석
- §3.4 왜 이전엔 안 터졌나: 회귀 분석 — 어떤 가정이 깨졌는가 (라이브러리 도입, 데이터 형식 변경 등)

분석 자료가 부족하면 사용자에게 추가 입력(스택트레이스, 재현 데이터, DevTools 스크린샷 위치 등)을 요청한다.

### 5. 파일명 결정

**규칙**: `<원본_티켓>_error.md`

```
docs/error/<원본_티켓_파일명>_error.md
```

예:
- 원본: `TRIX_EDITOR_INTEGRATION` → `docs/error/TRIX_EDITOR_INTEGRATION_error.md`
- 원본: `USER_PROFILE_IMAGE` → `docs/error/USER_PROFILE_IMAGE_error.md`

같은 원본 티켓에서 두 번째 에러가 발생하면 `_error_2`, `_error_3` 처럼 뒤에 번호를 붙이고 사용자에게 알린다. 기존 파일은 절대 덮어쓰지 않는다.

### 6. 에러 티켓 본문 작성

`docs/error/_template.md` 구조를 따른다. 이 스킬이 채우는 절은 **헤더 + §1 + §2 + §3** 까지. §4·§5·§6 은 placeholder 그대로 유지하고 후속 `/impl-*` 가 채운다.

#### 6.1 헤더 메타데이터 (필수 4개)

```markdown
# {{에러 한 줄 제목}}

발생 시점: {{오늘 날짜 YYYY-MM-DD}}
관련 티켓: `docs/tickets/{working|done}/<원본_티켓>.md`
관련 보고서: `docs/analysis/<...>_report.md`   (또는 `(없음)`)
영향 파일: `<핵심 영향 파일 경로>`
```

- "에러 한 줄 제목" 은 증상 + 추정 원인 한 문장 (예: "Trix 첨부 JSON 의 HTML 이중 디코드로 인한 SyntaxError")
- 발생 시점은 오늘 날짜로 채운다. 사용자가 다른 날짜를 명시했으면 그 값 사용.

#### 6.2 §1 증상

3단계에서 추출한 슬롯을 그대로 채운다. 콘솔/로그 원문은 코드 블록으로 보존.

#### 6.3 §2 의도 · 실제 동작 · 수정 방향

각 항목 한 줄로 압축. 30초 안에 사건을 파악할 수 있어야 한다.

#### 6.4 §3 근본 원인

4단계 분석 결과를 4개 하위 절(3.1~3.4)에 채운다. 단계별 추적표(§3.2)는 "단계 / 처리 / 결과" 3열 구조로 반드시 포함.

#### 6.5 §4 ~ §6 (placeholder 유지)

이 스킬은 §4·§5·§6 을 채우지 않는다. `_template.md` 의 placeholder 그대로 두고 다음 안내 주석을 §4 직전에 한 줄 추가한다:

```markdown
> **§4·§5 는 후속 `/impl-api` 또는 `/impl-front` 가 채운다. 본 스킬은 §3 까지 작성한다.**
```

### 7. 저장 (확인 없이 바로 실행)

`Write` 도구로 `docs/error/<원본_티켓>_error.md` 생성. **사용자에게 재확인 받지 않고 바로 저장.**

저장 전 중단 사유:
- 원본 티켓을 찾을 수 없음
- 동일 파일명이 이미 존재 (`_error_2` 등으로 안내)
- 사용자 입력이 §1·§2 의 필수 슬롯조차 채울 수 없을 정도로 모호
- 원본 티켓의 Scope 금지 항목을 침범해야만 성립하는 수정 방향

### 8. 완료 보고 + 후속 스킬 안내

저장 후 사용자에게 보고:

- 생성된 파일 경로
- 원본 티켓 / 영향 파일 요약
- **다음 단계 안내** — 영향 파일을 보고 아래 규칙으로 후속 스킬을 결정한다.

#### 후속 스킬 결정 규칙

§3 근본 원인 분석에서 식별된 **수정 대상 파일** 을 검토하여:

| 조건 | 추천 스킬 |
|------|-----------|
| 수정 대상이 **전부** `src/main/resources/templates/**` 또는 `src/main/resources/static/**` 하위 (= Java 파일 수정 없음, DB/설정 변경 없음) | `/impl-front` |
| 위 외의 모든 경우 (Java 코드, 엔티티, DTO, DB 스키마, 설정 파일 등 백엔드 변경 포함) | `/impl-api` |

판단 보강 신호:
- 수정 방향이 JavaScript / CSS / HTML 만 다룸 → `/impl-front`
- 컨트롤러 / 서비스 / 리포지토리 / 엔티티 / DTO 변경 언급 → `/impl-api`
- DB 스키마(`database.sql`) 변경 언급 → `/impl-api`

위 규칙으로 결정한 스킬을 다음 형식으로 안내한다:

```
구현을 시작하려면:
/impl-api docs/error/<원본_티켓>_error.md
```
또는
```
구현을 시작하려면:
/impl-front docs/error/<원본_티켓>_error.md
```

판단이 애매한 경우(백엔드/프론트 경계가 모호) 두 스킬을 모두 제시하고 사용자 선택을 요청.

**여기서 Skill 실행 종료.** 브랜치 생성/커밋/구현은 수행하지 않는다.

## 금지 사항

- 사용자 입력에 없는 증상/의도/수정 방향을 추측해서 채우기 금지
- `_template.md` 구조에서 헤더 4개 메타데이터·§1·§2·§3 절 임의 생략 금지
- §4·§5·§6 절을 이 스킬이 채우기 금지 (후속 `/impl-*` 의 몫)
- `docs/error/` 외 위치에 저장 금지
- 파일 생성 후 `git add` / 브랜치 생성 / 커밋 / push 금지
- 기존 `<원본_티켓>_error.md` 덮어쓰기 금지 (`_error_2`, `_error_3` 으로 분기)
- 원본 티켓을 찾지 못한 상태로 진행 금지
- 시크릿(DB URI, API 키 등) 하드코딩 금지

## 실패 처리

- 원본 티켓 미발견 → 중단 후 정확한 파일명 요청
- 동일 에러 파일명 존재 → `_error_N` 으로 변경하고 사용자에게 알림
- 사용자 입력 모호 → 질문 후 답변 대기, 임의 해석 금지
- 코드 분석 자료 부족(스택트레이스 / 재현 데이터 부재) → 사용자에게 보완 요청 후 §3 작성
