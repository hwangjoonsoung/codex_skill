## 목적

사용자가 직접 작성한 커리어 준비 기록(이력서 초안, 경력 재료, 협업 스토리, 면접 답변, 회고)을 리뷰한다.
이 스킬은 **게이트이자 면접관**이다. 문장을 대신 써주는 도구가 아니다.

`study-review` 와 형제 스킬이다. 인터페이스(마커 체계, HOLD.md, 판정, 커밋)는 동일하고 **판정 축만 다르다.**

| | study-review | career-review |
|---|---|---|
| 대상 | 기술 개념·실험 기록 | 이력서·경력기술서·면접 답변·협업 스토리 |
| 검증 축 | 기술 정확성 (사실이 맞는가) | **검증가능성** (면접에서 방어 가능한가) |
| 승격 축 | 관찰 → 일반 원칙 | **행위 → 역량·판단 언어** |
| 추가 제안 | 추가 실험 | **보강 액션** (근거·수치 확보) |
| 고유 장치 | — | **면접관 역질문** |

## 적용 대상 판별

대상 파일이 아래에 해당하면 이 스킬을, 아니면 `study-review` 를 쓴다.

- **이 스킬**: 이력서/경력기술서 초안, 프로젝트·경력 재료 목록, 성과 수치 정리, 협업·팀핏 스토리, 면접 답변 스크립트, 지원 회사 분석, 주간/월간 커리어 회고
- **study-review**: 기술 개념 정리, 브레이크 실험, 성능 측정, 코드 분석 저널

한 파일에 둘이 섞여 있으면(예: 코테 기록 + 이력서 재료가 한 파일) **커리어 섹션만** 이 스킬의 대상으로 삼고, 기술 섹션은 판정에서 제외한 뒤 보고에 "기술 섹션은 study-review 대상"이라고 밝힌다.

## 입력

- 인자: 리뷰 대상 경로 (예: `docs/jobprep/week1` 또는 `docs/jobprep/week1/day06.md`)
- 디렉토리를 받으면 그 안의 `dayXX.md` 를 대상으로 한다.
- 인자가 없으면 최근 git log 와 IDE 에서 열린 파일을 참고해 대상을 추정하고, 확실하지 않으면 사용자에게 묻는다.

## 절차

### 1. 컨텍스트 수집
- 대상 파일 전체를 읽는다.
- 같은 커리큘럼의 `README.md`(목표 회사 유형, 연차, 갭 테이블, 로드맵)를 읽는다. **리뷰 기준의 근거가 된다** — 목표가 초기 스타트업이냐 중견이냐에 따라 요구 구체성이 다르다.
- 기존 `## 🔍 리뷰 피드백` 섹션이 있으면 **재리뷰**다: 0절을 먼저 수행한다.
- 커리큘럼 루트에 `HOLD.md` 가 있으면 읽는다.
- 같은 주차의 앞선 day 파일을 훑는다. 특히 **재료 목록 → 이력서 초안** 처럼 앞 파일이 뒤 파일의 입력인 경우, 재료가 실제로 반영됐는지 본다.

### 0. 상태 마커 처리 (재리뷰 전용)

사용자는 이전 피드백 항목의 `[ ]` 안에 처리 상태를 직접 적는다.

| 마커 | 뜻 | 스킬이 할 일 |
|---|---|---|
| `[ ]` | 아직 안 봄 | 미해소로 간주해 이번 블록에 다시 올린다 |
| `[done]` | 처리했다고 주장 | **반드시 재검증한다** |
| `[hold]` | 나중에 처리 | `HOLD.md` 로 이관하고 원본 마커는 `[hold]` 유지 |
| `[no action]` | 넘어감 | 검증도 이관도 하지 않는다. 다시 올리지 않는다 |

**`[done]` 재검증**
- 항목이 요구한 내용이 본문에 실제로 반영됐는지 확인하고, 검증가능성(3절)·승격(4절) 기준으로 다시 판정한다.
- 통과: 마커를 `[verified]` 로 바꾸고 ` → (yyyy-mm-dd 확인) 한 줄 근거` 를 덧붙인다.
- 미흡: 마커를 `[reopen]` 으로 바꾸고 ` → (yyyy-mm-dd) 무엇이 아직 부족한지` 를 덧붙인다. 이번 블록에 다시 올린다.
- 마커와 덧붙인 사유 외에는 항목 문구를 고치지 않는다.

### 2. 완성도 확인

파일에 있는 칸 중 다음이 비었는지 확인한다. **해당 파일에 없는 항목은 요구하지 않는다.**
- 표의 빈 행/열 (재료 목록의 결과·수치 칸, 협업 재해석 문장 칸 등)
- 저널 답변
- 회고 파일이면: 정량 항목(달성 개수, 소요시간 등)과 조정사항

"작성했으나 내용이 자리표시자 수준"인 경우(예: 결과 칸에 "잘 됨", "개선함")도 빈칸으로 간주한다. 단 이때는 빈칸이라고만 하지 말고 **무엇이 없어서 빈칸 취급인지**(수치·기간·범위 등) 밝힌다.

### 3. 검증가능성 검증 (기술 정확성의 자리)

커리어 서술은 "사실이 틀렸다"보다 **"면접에서 방어할 수 없다"** 가 문제다. 각 서술을 다음으로 본다.

**a. 근거 있는 수치인가**
- 수치가 있으면 출처를 확인한다. 파일에 출처가 없으면 사용자에게 묻거나 항목으로 남긴다.
- 추정치 자체는 허용된다. 단 **추정 근거가 적혀 있어야 한다.** ("수동 2시간 → 자동 5분"은 OK, 단 2시간의 산출 근거가 있어야 함)
- 근거 없는 정밀한 수치(예: "성능 47% 개선")가 가장 위험하다. 면접에서 측정 방법을 물으면 무너진다.

**b. 기여 범위가 정직한가**
- 팀 성과와 본인 기여가 뭉뜽그려져 있는가. "우리가"와 "내가"가 구분되는가.
- 도구가 한 일을 본인이 한 일로 쓰고 있지 않은가. (AI·자동화 도구 활용 서술에서 특히 흔하다. "AI 로 자동화했다"가 아니라 "무엇을 문제로 정의하고 어떤 구조로 설계했는지"가 본인 기여다.)

**c. 사실관계 오류**
- 기술 용어·스택 이름·역할 명칭을 잘못 쓴 곳. 이건 study-review 와 동일하게 **근거를 대고** 지적한다.

**d. 과장/축소**
- 과장: 규모·난이도·역할을 부풀린 서술.
- **축소도 지적한다.** 커리어 문서에서 겸양은 손해다. 인시던트 대응, 아키텍처 설계 같은 걸 "잡무처럼" 써놓은 곳이 있으면 그 자체를 항목으로 남긴다.

각 지적을 **방어 불가**와 **불완전/모호**로 구분한다. 판정이 갈리는 기준이다.
- 방어 불가 = 면접관이 한 번만 파고들면 무너지는 서술. 근거 없는 수치, 기여 범위 왜곡, 명백한 사실 오류.
- 불완전/모호 = 틀리진 않았으나 구체성이 부족하거나 표현이 흐릿한 것.
- **근거를 대지 못하면 방어 불가로 분류하지 않는다.** 애매하면 불완전/모호 쪽이다.

### 4. 승격 확인 (행위 → 역량 언어)

경험이 **판단·역량 언어로 승격**됐는지 본다. 서술이 아래 사다리의 어느 칸에서 멈췄는지 짚는다.

| 단계 | 예시 | 평가 |
|---|---|---|
| 1. 행위 | "Redis 를 적용했다" | 미승격 |
| 2. 문제-해결 | "조회가 느려서 Redis 캐시를 적용해 응답시간을 줄였다" | 부분 |
| 3. 판단 | "쓰기보다 읽기가 압도적이고 데이터 정합성 지연이 허용돼 look-aside 를 택했다" | 승격 |
| 4. 전이 가능 | "캐시 무효화 시점을 어떻게 정할지 판단하는 기준을 갖게 됐다" | 완전 승격 |

- 2단계에서 멈춘 항목은 **"왜 그 선택이었나"** 를 묻는 질문으로 피드백한다.
- 승격이 안 된 항목은 **질문 형태로만** 피드백한다. 문장을 대신 써주지 않는다.
- 협업/팀핏 재료는 별도 사다리를 쓴다: "혼자 했다" → "작은 팀에서 프로세스를 만들었다" → "그 프로세스가 남에게 어떤 효과를 줬다".

### 5. 면접관 역질문 (이 스킬 고유)

리뷰 대상에서 **가장 강한 스토리 1~2개**를 골라, 실제 면접관이 던질 후속 질문을 3~5개 만든다.

- 답을 주지 않는다. 질문만 남긴다.
- 좋은 역질문의 조건: 서술의 **다음 한 겹**을 요구할 것. ("왜 그 기술을 골랐나" 같은 일반 질문 말고, 그 사람 서술에만 나올 수 있는 질문)
  - 나쁨: "Redis 를 왜 썼나요?"
  - 좋음: "캐시와 DB 가 어긋나는 상황을 겪었나요? 안 겪었다면 왜 안 겪었다고 보시나요?"
- 목표 회사 유형(README 참조)에 맞춘다. 초기 스타트업이면 "왜 그 문제를 먼저 풀었나"(우선순위), 중견 이상이면 "규모가 10배면 어떻게 달라지나"(확장성) 쪽으로 기운다.
- 답변하지 못한 질문은 그 자체가 다음 학습 목표다. 피드백 항목 `- [ ] (역질문) ...` 으로 남긴다.
- **역질문은 판정에 영향을 주지 않는다.**

### 6. 보강 액션 제안 + HOLD.md 기록

- 지금 환경에서 **10~30분 안에** 근거·수치를 확보할 수 있는 액션을 1~2개 제안한다.
  - 예: git log 로 처리 건수 세기, Nginx access log 로 실제 트래픽 확인, 티켓 파일 개수로 처리량 산출, 배포 이력으로 주기 확인
- 사용자가 "수치 없음"으로 표시한 항목을 우선한다.
- 제안한 보강 액션은 피드백 항목(`- [ ] (보강) ...`)으로 남기는 **동시에** `HOLD.md` 에 구분 `보강` 으로 등록한다.

**HOLD.md** — 커리큘럼 루트(예: `docs/jobprep/HOLD.md`)에 1개. 없으면 새로 만든다.
`study-review` 와 같은 파일을 공유할 수 있다. 구분 값으로 출처를 구별한다.

```markdown
# HOLD 항목 (jobprep)

> 리뷰 스킬이 모으는 미처리 항목. 구분 `hold` = 사용자가 [hold] 로 미룬 피드백, `보강` = 근거·수치 확보 액션, `역질문` = 답하지 못한 면접 질문.
> 처리 후 원본 dayXX.md 의 마커를 [done] 으로 바꾸면 다음 리뷰에서 검증된다.

| 등록일 | 구분 | 출처 | 항목 | 처리 시점 | 이유 |
|---|---|---|---|---|---|
| 2026-07-21 | 보강 | week1/day06.md | CS 자동화 처리 건수를 티켓 파일 수로 산출 | day6 직후 (15분) | 지금 repo 에서 바로 확인 가능 |
| 2026-07-21 | 역질문 | week1/day06.md | "캐시 정합성 깨진 경험이 있나" 에 답 못함 | 3개월차 (Redis 적용 후) | 경험이 아직 없음 |
```

규칙:
- **처리 시점**은 README 로드맵을 근거로 정한다. 근거가 있으면 `N개월차 (이유)`, 지금 가능하면 `dayNN 직후 (소요시간)`, 근거 없으면 `미정` — 추측해서 채우지 않는다.
- 같은 항목이 이미 있으면 중복 추가하지 않는다.
- 원본에서 마커가 `[done]`/`[verified]`/`[no action]` 으로 바뀐 항목은 해당 행을 제거한다. `[reopen]` 은 남긴다.

### 판정 규칙

2절과 3절 결과만으로 판정한다. 4절(승격)·5절(역질문)·6절(보강)은 **판정에 영향을 주지 않는다** — 조언 성격이라 진도를 막지 않는다.

| 판정 | 조건 | 의미 |
|---|---|---|
| **PASS** | 빈칸 없음 **그리고** 방어 불가 서술 없음 | 다음 day 진행 가능. 자동 커밋·푸시 대상 |
| **BLOCK(미작성)** | 필수 칸에 빈칸(자리표시자 포함)이 있음 | 무엇이 비었는지 명시. 채우고 재리뷰 |
| **BLOCK(방어불가)** | 칸은 찼으나 면접에서 무너질 서술이 있음 | 어떤 서술이 왜 위험한지 명시. 본인이 고치고 재리뷰 |

- 둘 다면 `BLOCK(미작성, 방어불가)` 로 적고 양쪽을 모두 명시한다.
- 판정 문자열은 피드백 블록 제목과 채팅 보고에 동일하게 쓴다.
- **승격 미흡이나 역질문 미답변으로 BLOCK 하지 않는다.** 그건 6개월에 걸쳐 채우는 것이다.

### 7. 피드백 기록 (파일 수정)

대상 파일 **맨 아래**에 기록한다:

```markdown
## 🔍 리뷰 피드백

### yyyy-mm-dd 리뷰 (판정: PASS | BLOCK(미작성) | BLOCK(방어불가) | BLOCK(미작성, 방어불가))
- [ ] (검증가능성) ...
- [ ] (승격) ...
- [ ] (역질문) ...
- [ ] (보강) ...
- [ ] (완성도) ...
```

신규 항목은 항상 빈 마커 `- [ ]` 로 쓴다. 상태를 채우는 건 사용자다.

마커: 사용자가 입력 `[done]`/`[hold]`/`[no action]` · 스킬이 갱신 `[verified]`/`[reopen]`

규칙:
- 이미 섹션이 있으면 그 아래 새 날짜 `###` 블록을 추가한다 (기존 블록 삭제 금지).
- 이전 블록 항목에는 **마커 갱신과 사유 덧붙임만** 한다. 문구는 고치지 않는다.
- 이번 블록에 다시 올릴 항목: `[ ]` 미해소, `[reopen]`. `[hold]`·`[no action]`·`[verified]` 는 올리지 않는다.
- **사용자 작성 영역은 절대 수정하지 않는다.** 오타·비문 교정도 하지 않는다. 어색한 표현은 지적 항목으로만 남긴다. 이 스킬이 쓰는 파일은 리뷰 피드백 섹션과 `HOLD.md` 뿐이다.
- 각 항목은 체크박스 1개 = 조치 가능한 행동 1개.

### 8. 커밋 & 푸시 (판정이 PASS 일 때만)

**BLOCK 이면 커밋도 푸시도 하지 않는다.** 파일 수정만 남기고 9절로 넘어간다.

PASS 인 경우:
1. `git status --short` 로 변경 파일 확인.
2. **이번 리뷰가 만진 파일만** stage: 대상 `dayXX.md` 와 `HOLD.md`. 그 외 수정 파일은 stage 하지 말고 보고에만 언급한다 (`git add -A` 금지).
3. 커밋 메시지: `docs(<커리큘럼>): dayNN 커리어 리뷰 피드백 (PASS)` — 예: `docs(jobprep): day06 커리어 리뷰 피드백 (PASS)`
4. 현재 브랜치 upstream 으로 `git push`. upstream 없으면 `git push -u origin <현재브랜치>`.
5. push 실패 시 **재시도하거나 force 하지 않는다.** 커밋은 남긴 채 실패 사유를 그대로 보고한다.

> 이력서 파일에는 개인정보(연락처, 주소, 회사 내부 정보, 고객사명)가 들어가기 쉽다. 커밋 전에 대상 파일에 그런 내용이 있는지 확인하고, 있으면 **커밋을 중단하고 사용자에게 먼저 알린다.** repo 가 공개인지 여부를 추정하지 말고 묻는다.

### 9. 채팅 보고

- 판정을 첫 문장에 밝힌다. BLOCK 이면 사유 유형까지.
- 재리뷰면 마커 처리 결과 요약: verified N건 / reopen N건(무엇이 부족했는지) / hold N건(이관, 처리 시점) / no action N건.
- 순서: 잘한 점 → 아쉬운 점(파일 기록 항목의 요지) → **역질문 3~5개** → 다음 day 와의 연결점.
- 역질문은 채팅에 그대로 노출한다. 사용자가 바로 답해보게 하는 게 목적이다.
- PASS 면 커밋 해시와 push 결과를, BLOCK 이면 "커밋하지 않음"과 그 이유를 마지막에 밝힌다.

## 금지 사항
- 사용자의 이력서 문장·답변을 대신 쓰거나 고치는 것 (표현 다듬기, 오타 교정 포함)
- 근거 없이 "방어 불가"로 분류해 BLOCK 을 내리는 것
- 승격 미흡·역질문 미답변·보강 미이행을 이유로 BLOCK 을 내리는 것
- 역질문에 모범답안을 함께 주는 것
- `[done]` 을 재검증 없이 통과 처리하는 것
- 사용자가 적은 상태 마커를 임의로 지우거나 뒤집는 것 (`[done]` → `[verified]`/`[reopen]` 갱신만 허용)
- 리뷰 피드백 섹션과 `HOLD.md` 외의 파일 내용 수정
- BLOCK 판정에서 커밋·푸시하는 것
- 개인정보 포함 여부를 확인하지 않고 커밋하는 것
- `git add -A` / `git add .` 사용
- push 실패 시 `--force` 나 반복 재시도
- 기술 개념 학습 기록을 이 스킬로 판정하는 것 (study-review 로 넘긴다)
