## 목적

사용자가 직접 작성한 학습 기록(브레이크 실험, 저널 답변, 요약)을 리뷰한다.
이 스킬은 **게이트이자 코치**다. 답을 대신 써주는 도구가 아니다.

## 입력

- 인자: 리뷰 대상 경로 (예: `docs/nginx/day1` 또는 `docs/nginx/day1/day01.md`)
- 디렉토리를 받으면 그 안의 `dayXX.md`를 대상으로 한다.
- 인자가 없으면 최근 git log와 IDE에서 열린 파일을 참고해 대상을 추정하고, 확실하지 않으면 사용자에게 묻는다.

## 절차

### 1. 컨텍스트 수집
- 대상 dayXX.md 전체를 읽는다.
- 같은 커리큘럼의 `README.md`(학습 원칙, 로드맵)를 읽는다.
- 대상 파일에 기존 `## 🔍 리뷰 피드백` 섹션이 있으면 **재리뷰**다: 이전 피드백 항목의 상태 마커를 먼저 읽고 [상태 마커 처리](#0-상태-마커-처리-재리뷰-전용)를 수행한다.
- 커리큘럼 루트에 `HOLD.md`가 있으면 읽는다 (기존 hold 항목 파악).
- 바로 다음 day 파일의 학습 목표를 훑어 연결점을 파악한다.

### 0. 상태 마커 처리 (재리뷰 전용)

사용자는 이전 리뷰 피드백 항목의 `[ ]` 안에 처리 상태를 직접 적는다.

| 마커 | 뜻 | 스킬이 할 일 |
|---|---|---|
| `[ ]` | 아직 안 봄 | 미해소로 간주해 이번 블록에 다시 올린다 |
| `[done]` | 처리했다고 주장 | **반드시 재검증한다** (아래) |
| `[hold]` | 나중에 처리 | `HOLD.md`로 이관하고 원본 항목은 `[hold]` 유지 |
| `[no action]` | 넘어감 | 검증도 이관도 하지 않고 그대로 둔다. 다시 올리지 않는다 |

**`[done]` 재검증**
- 해당 항목이 요구한 내용이 dayXX.md 본문에 실제로 반영됐는지 확인하고, 기술 검증(3절)과 승격 확인(4절) 기준으로 다시 판정한다.
- 통과: 마커를 `[verified]`로 바꾸고 항목 끝에 ` → (yyyy-mm-dd 확인) 한 줄 근거`를 덧붙인다.
- 미흡: 마커를 `[reopen]`으로 바꾸고 ` → (yyyy-mm-dd) 무엇이 아직 부족한지`를 덧붙인다. 이번 날짜 블록에 후속 항목으로 다시 올린다.
- 마커와 덧붙인 사유 외에는 항목 문구를 고치지 않는다.

**`[hold]` 이관**
- 구분 `hold` 로 `HOLD.md`(→ 5절)에 기록하고, dayXX.md 원본 항목의 마커는 `[hold]` 그대로 둔다.

### 2. 완성도 확인
다음이 모두 채워졌는지 확인한다:
- 브레이크 실험 기록: 각 실험의 **예상 / 실제 결과 / 배운 점**
- 저널 질문 답변
- 오늘의 한 줄 요약

빈칸이 하나라도 있으면 무엇이 비었는지 명시한다. (판정은 3절 이후 종합 → [판정 규칙](#판정-규칙))

### 3. 기술 검증
- 사용자가 기록한 관찰·결론·저널 답변이 기술적으로 정확한지 검증한다.
- **추측으로 판정하지 않는다.** 확신이 없으면 공식 문서(nginx.org docs 등 해당 커리큘럼 README의 자료 링크)를 확인하거나, 로컬에서 재현 가능하면 직접 확인한 뒤 판정한다.
- 부정확한 서술은 "무엇이, 왜 틀렸고, 정확한 사실은 무엇인지"까지 설명한다. 단 수정 문장을 대신 써넣지는 않는다.
- 각 지적을 **명백한 오류**와 **불완전/모호**로 구분해 둔다. 판정이 갈리는 기준이다.
  - 명백한 오류 = 사실관계가 틀림. 공식 문서나 직접 재현으로 반증할 수 있는 서술.
  - 불완전/모호 = 틀리진 않았지만 설명이 부족하거나 표현이 흐릿한 것.
  - **근거를 대지 못하면 명백한 오류로 분류하지 않는다.** 애매하면 불완전/모호 쪽이다.

### 4. 승격 확인
- 관찰이 일반 원칙으로 정리됐는지 본다.
  (예: "worker가 재생성됐다"에서 멈추면 지적 → "master가 SIGCHLD로 감지해 새 worker를 fork한다"처럼 한 단계 위 원칙으로 승격하도록 유도)
- 승격이 안 된 항목은 힌트가 되는 **질문** 형태로 피드백한다. 답을 주지 않는다.

### 5. 추가 실험 제안 + HOLD.md 기록

- 지금 환경(실행 중인 컨테이너 등)에서 5~10분 안에 확인 가능한 추가 실험을 1~2개 제안한다.
- 사용자가 스스로 궁금해했지만 확인하지 못한 지점을 우선한다.
- 제안한 추가 실험은 dayXX.md 피드백 항목(`- [ ] (추가 실험) ...`)으로 남기는 **동시에** `HOLD.md`에도 구분 `실험` 으로 등록한다. 리뷰가 끝나면 잊히기 쉬운 항목이라 한곳에 모아둔다.

**HOLD.md** — 커리큘럼 루트(예: `docs/nginx/HOLD.md`)에 1개. 없으면 새로 만든다.

```markdown
# HOLD 항목 (nginx)

> study-review 가 모으는 미처리 항목. 구분 `hold` = 사용자가 [hold] 로 미룬 피드백, `실험` = 리뷰에서 제안된 추가 실험.
> 처리 후 원본 dayXX.md 의 마커를 [done] 으로 바꾸면 다음 리뷰에서 검증된다.

| 등록일 | 구분 | 출처 | 항목 | 처리 시점 | 이유 |
|---|---|---|---|---|---|
| 2026-07-21 | hold | day1/day01.md (승격) | worker 재생성 경로를 signal 관점으로 정리 | day3 (signal 다루는 날) | 선행 지식 필요 |
| 2026-07-21 | 실험 | day1/day01.md | master PID 에 SIGTERM 후 worker 상태 관찰 | day1 직후 (5분) | 지금 컨테이너에서 바로 확인 가능 |
```

규칙:
- **처리 시점**은 커리큘럼 README 로드맵을 근거로 정한다. 근거가 있으면 `dayNN (이유)`, 지금 바로 가능한 실험이면 `dayNN 직후 (소요시간)`, 근거가 없으면 `미정` — 추측해서 채우지 않는다.
- 같은 항목이 이미 있으면 중복 추가하지 않는다.
- 원본 dayXX.md 에서 마커가 `[done]`/`[verified]`/`[no action]`으로 바뀐 항목은 HOLD.md 에서 해당 행을 제거한다. `[reopen]`은 남겨둔다.

### 판정 규칙

2절과 3절 결과를 종합해 판정한다. 4절(승격)과 5절(추가 실험)은 **판정에 영향을 주지 않는다** — 조언 성격이라 진도를 막지 않는다.

| 판정 | 조건 | 의미 |
|---|---|---|
| **PASS** | 빈칸 없음 **그리고** 명백한 기술 오류 없음 | 다음 day 진행 가능. 자동 커밋·푸시 대상 |
| **BLOCK(미작성)** | 필수 칸에 빈칸이 있음 | 무엇이 비었는지 명시. 채우고 재리뷰 |
| **BLOCK(오류)** | 칸은 다 찼으나 명백한 기술 오류가 있음 | 어떤 서술이 왜 틀렸는지 명시. 본인이 고치고 재리뷰 |

- 둘 다 해당하면 `BLOCK(미작성, 오류)`로 적고 양쪽을 모두 명시한다.
- 판정 문자열은 피드백 블록 제목과 채팅 보고에 동일하게 쓴다.

### 6. 피드백 기록 (파일 수정)
대상 dayXX.md **맨 아래**에 다음 형식으로 기록한다:

```markdown
## 🔍 리뷰 피드백

### yyyy-mm-dd 리뷰 (판정: PASS | BLOCK(미작성) | BLOCK(오류) | BLOCK(미작성, 오류))
- [ ] (기술 정확성) ...
- [ ] (승격) ...
- [ ] (추가 실험) ...
- [ ] (완성도) ...
```

신규 항목은 항상 빈 마커 `- [ ]`로 쓴다. 상태를 채우는 건 사용자다.

사용 가능한 마커:
- 사용자가 입력: `[done]` / `[hold]` / `[no action]`
- 스킬이 갱신: `[verified]` / `[reopen]` (0절의 `[done]` 재검증 결과)

규칙:
- 이미 `## 🔍 리뷰 피드백` 섹션이 있으면 그 아래에 새 날짜의 `###` 블록을 추가한다 (기존 블록 삭제 금지).
- 이전 블록 항목에는 0절 결과에 따른 **마커 갱신과 사유 덧붙임만** 한다. 항목 문구 자체는 고치지 않는다.
- 이번 블록에 다시 올릴 항목: 마커가 `[ ]`인 미해소 항목, `[reopen]`으로 판정된 항목. `[hold]`·`[no action]`·`[verified]`는 다시 올리지 않는다.
- **사용자 작성 영역(브레이크 실험 기록, 저널 답변, 한 줄 요약 등)은 절대 수정하지 않는다.** 오타 교정도 하지 않는다. 이 스킬이 쓰는 파일은 리뷰 피드백 섹션과 커리큘럼 루트 `HOLD.md` 뿐이다.
- 각 항목은 체크박스 1개 = 조치 가능한 행동 1개 단위로 쓴다.

### 7. 커밋 & 푸시 (판정이 PASS 일 때만)

**BLOCK 이면(미작성이든 오류든) 커밋도 푸시도 하지 않는다.** 파일 수정만 남기고 8절로 넘어간다.

PASS 인 경우:
1. `git status --short` 로 변경 파일을 확인한다.
2. **이번 리뷰가 만진 파일만** stage 한다: 대상 `dayXX.md` 와 커리큘럼 루트 `HOLD.md`. 그 외에 수정된 파일이 있으면 stage 하지 말고 보고에만 언급한다 (`git add -A` 금지).
3. 커밋 메시지: `docs(<커리큘럼>): dayNN 리뷰 피드백 (PASS)` — 예: `docs(nginx): day01 리뷰 피드백 (PASS)`
4. 현재 브랜치의 upstream 으로 `git push` 한다. upstream 이 없으면 `git push -u origin <현재브랜치>`.
5. push 가 실패하면(비 fast-forward, 권한, 원격 없음 등) **재시도하거나 force 하지 않는다.** 커밋은 남긴 채 실패 사유를 그대로 보고한다.

### 8. 채팅 보고
- 판정(PASS / BLOCK(미작성) / BLOCK(오류) / BLOCK(미작성, 오류))을 첫 문장에 밝힌다. BLOCK 이면 사유 유형까지 함께 말한다.
- 재리뷰면 상태 마커 처리 결과를 요약한다: verified N건 / reopen N건(무엇이 부족했는지) / hold N건(HOLD.md 이관, 처리 시점) / no action N건.
- 잘한 점 → 아쉬운 점(파일에 기록한 항목의 요지) → 다음 day와의 연결점 순으로 보고한다.
- PASS 면 커밋 해시와 push 결과를, BLOCK 이면 "커밋하지 않음"과 그 이유(어느 칸이 비었는지 / 어떤 서술이 왜 틀렸는지)를 마지막에 밝힌다.

## 금지 사항
- 사용자 답변 칸을 대신 채우거나 고치는 것
- 근거 확인 없이 기술 판정을 내리는 것
- 반증 근거 없이 "명백한 오류"로 분류해 BLOCK(오류)를 내리는 것
- 승격 미흡·추가 실험 미이행을 이유로 BLOCK 을 내리는 것
- `[done]`을 재검증 없이 통과 처리하는 것
- 사용자가 적은 상태 마커를 임의로 지우거나 뒤집는 것 (`[done]` → `[verified]`/`[reopen]` 갱신만 허용)
- 리뷰 피드백 섹션과 `HOLD.md` 외의 파일 내용 수정
- BLOCK 판정에서 커밋·푸시하는 것
- `git add -A` / `git add .` 로 관련 없는 파일까지 stage 하는 것
- push 실패 시 `--force` 나 반복 재시도
